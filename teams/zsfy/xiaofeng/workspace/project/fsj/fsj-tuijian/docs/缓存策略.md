## 2. 背景与实测

页面 = 小程序 web-view 内嵌 H5（抖音式竖滑内容流）。上线后反馈加载慢，实测根因：

| 资源 | 现状源 | 实测 | 结论 |
|------|--------|------|------|
| 视频 ×18 条 mock | test-videos.co.uk | 2.57s / 1MB（~390KB/s） | 境外慢源，最大瓶颈 |
| 头像 ×30 | i.pravatar.cc | 403 被拒 | 不可用，换本地 SVG 生成 |
| 占位图 ×39 | picsum.photos | 302 跳转 + 0.9s 起 | 境外 + 多一跳 |
| Font Awesome | jsdelivr CDN | 0.42s | 有国内节点，可用 |
| 预加载策略 | 无 | — | 滑到才下载，滑动必等 |
| 静态版本号 | `?v=Date.now()` | — | 每次进页 CSS/JS 缓存全废 |

**决策**：媒体源问题归属 Stage 2 数据源方案（动态内容该挂 CDN/对象存储，不落宝塔——宝塔容量有限，老板拍板）。本次只做与数据源解耦的代码层优化，Stage 2 直接复用。

## 3. 通俗版（老板版）

比喻：页面是餐厅，视频图片是菜。

1. **提前备菜**：你看当前视频时，手机已偷偷下载好下一条。一滑，秒出。
2. **先上菜再备菜**：第一条视频没出来前，不许备下一条——防止抢网速让首屏更慢。
3. **两个炉子交接班**：固定 2 个播放器（1 个台前播、1 个幕后备），滑动是交接，不是拆了重装。只 2 个是因为播放器吃内存，多了手机发烫卡死。
4. **不盯空盘子**：下载中先给封面图 + 转圈圈，眼里有东西就不觉得慢。
5. **记住装修手册**：页面骨架（CSS/JS）很小但每次进店都重新下载，改成记住，发新版才更新。二次进店明显快。
6. **数据只记临时脑记**：往回滑，看过的内容立刻回来（本次打开期间有效）；关掉重进重新拉——微信内网页的"小本本"会被随手清掉，靠不住。

**不做**：不把菜存自家小仓库（宝塔小，数据以后是海量的）；不玩高级离线缓存（SW 在微信里时灵时不灵）。

## 4. 技术版设计

### 4.1 视频实例池 + 双缓冲（B2'，核心）

```
实例池：2 个 <video> 元素循环复用（slot A / slot B）

状态机：
  slot-A: PLAYING（当前卡片）
  slot-B: PRELOADING（下一卡片，隐藏、静音、preload=auto、不进可视区）

滑动切换流程：
  1. 用户上滑 → slot-B（已预载）滑入可视区 → play()
  2. 原 slot-A 滑出 → pause() → 清空 src → 变为空闲槽
  3. 新的"下一卡片"数据装入空闲槽 → 预载
  4. 循环往复，任何时刻只有 2 个 video 实例存在

预载闸门（防抢首屏带宽）：
  当前视频 canplay 事件触发后 → 才允许启动下一卡预载
  首屏冷启动路径：HTML → 数据 → 首视频，全程无竞争

销毁纪律：
  视频离开可见 → pause() + removeAttribute('src') + load()
  页面 destroy() → 两个槽全部释放
```

内存红线：**2 个 video 封顶**（iOS WKWebView 内存超限会杀整个小程序；视频解码是内存大户）。

### 4.2 图片预加载（B1）

```javascript
// 预载时机：当前卡片首帧稳定后；并发上限 2
// 预载对象：下一卡片的封面/首图（图片卡则前 2 张）
const img = new Image();
img.src = nextItem.coverUrl;   // 下载后进入 HTTP 缓存 + 内存解码缓存
// 页面真正渲染该图时直接命中，零等待
```

### 4.3 静态资源版本号（C1）

```
现状：index.html 里 ?v=Date.now() —— 每次进页都变，CSS/JS 缓存全废
改为：deploy.mjs 部署时把 release 号（如 20260918093058-zobo）注入 index.html 的 ?v=
效果：HTML 保持禁缓存（meta 已有）；CSS/JS 长缓存，只有发新版才失效
依据：微信安卓 XWEB / iOS WKWebView 的 HTTP 缓存（Cache-Control/ETag）均正常工作
```

### 4.4 数据内存缓存（C2）

```javascript
// feed 数据内存 Map：会话内有效
// 用途：回滑命中（不重新渲染/重新拉详情）、页面内部返回秒开
// 不用 localStorage/sessionStorage：微信 webview 会清理本地存储，不可靠（模板教训）
// 不持久化：Stage 2 若需跨会话状态，走 URL 传参或小程序侧存储，不走 webview 本地
容量纪律：只保留最近 2 页 feed 的数据，旧的释放
```

### 4.5 加载体验兜底（D）

- poster 封面先行（已有）+ loading spinner（已有）
- 补：媒体加载中的渐变底色（与整体风格一致），消除"白屏感"
- 补：封面图加载失败的占位样式（断网/404 不裸奔）

### 4.6 明确不做

| 项 | 不做的理由 |
|----|-----------|
| 媒体存宝塔 | 数据动态且海量，宝塔容量有限（老板拍板）；等 Stage 2 数据源方案 |
| Service Worker | iOS WKWebView 支持、安卓 XWEB 不稳，双端行为不可控 |
| localStorage 持久化 | 微信 webview 会清理，不可靠 |
| postMessage 做实时通道 | 仅后退/销毁/分享时机批量送达，非实时；Stage 2 互动上报走 HTTP API 直连后端 |

## 5. 嵌套架构与缓存（老板担心 ①）

### 5.1 实际嵌套链路

```
微信小程序（wxApp-zsfy 原生页面）
 └── <web-view> 组件
       └── 加载 SPA（webview-spa2.0，https://100000whys.cn/fsj_webview2.0/）
             └── SPA hash 路由切换页面
                   └── #page-webview 页面内 <iframe id="webview-iframe"> 再嵌外部 H5
                       （如 hezi 盒子页，通过 postMessage 与 SPA 通信）
```

### 5.2 关键结论：缓存不会"每层存一份"

HTTP 缓存（磁盘缓存）归 **WebView 内核**管，不归某一"层"管：

- 缓存以 **URL 为 key**，全内核只有一份。小程序 web-view 里加载过的 `100000whys.cn/xxx.js`，iframe 里再加载同 URL **直接命中同一份**
- 三层结构**互相共享、互相命中**，不存在"套一层就多存一份"的放大效应
- 跨域名才分开存（比如 `100000whys.cn` 的资源和 `p1.mingdaoyun.cn` 的附件各是各的条目），但仍在同一个内核缓存池里

**一句话：套娃不放大缓存，只放大内存。**

### 5.3 嵌套的真正代价：内存叠加

每层是一个独立文档上下文（各自的 JS 堆、DOM、媒体解码器）：

| 层 | 内存开销 |
|----|----------|
| 小程序原生 | 固定 |
| web-view → SPA 主文档 | 中（DOM + JS） |
| iframe 内文档 | 又一份 DOM + JS |
| 其中的视频解码 | 大头（每路视频几十 MB 级） |

iOS 上内存超限 = 系统杀整个小程序（用户感受：闪退）。**层数越多、媒体越重，越接近红线。**

### 5.4 对 fsj-tuijian 的架构建议

fsj-tuijian 是**重媒体页**（全屏视频流），是内存最贵的页面类型：

1. **不要把 fsj-tuijian 塞进 SPA 的 iframe 页**——那会变成"web-view 里 iframe 里跑视频流"，内存三层叠加，iOS 风险高
2. 推荐两种安全形态（Stage 2 定）：
   - **平级页面**：作为 SPA 的一个原生路由模块（像 SPA 自己的页面那样动态加载），复用 SPA 的 web-view 层，**不新增 iframe 层**
   - **独立入口**：保持独立 URL（如现在 `100000whys.cn/tuijian/`），小程序里用独立页面 + web-view 直接加载，与 SPA 并列
3. 如果业务必须 iframe 嵌：**离开页面时卸载 iframe**（移除节点或清 src），不可见的层不留媒体实例

## 6. 缓存堆积与体验（老板担心 ②）

### 6.1 磁盘缓存：内核自动管，不用我们清

- WKWebView / XWEB 的磁盘缓存有**系统配额**（按设备磁盘空间动态调整）
- 满了自动 **LRU 清理**（最久不用的先扔），不会无限膨胀撑爆手机
- 对我们的影响：**热点内容命中率高 = 越刷越快**；冷门内容被挤掉 = 重下，属正常代谢
- 代价：占用用户手机存储（用户可在微信设置里清理；我们无法也不应干预）

**结论：磁盘缓存越多，用户体验通常越好（命中率），不需要也不应该手动清理。**

### 6.2 内存：必须我们主动管（方案已含）

内存堆积才是"缓存越多越卡"的真凶：

| 策略 | 落点 |
|------|------|
| video 实例池 2 个封顶 | § 4.1 |
| 离开可见立即释放（pause + 清 src） | § 4.1 销毁纪律 |
| feed 内存 Map 只留 2 页 | § 4.4 |
| 图片预载并发 ≤ 2 | § 4.2 |
| 页面 destroy() 全量释放 | 模板生命周期约定 |

**结论：磁盘随便攒（内核管），内存按红线管（我们管）。管住内存，缓存越多越快而不是越卡。**

### 6.3 唯一需要"清缓存"的场景

版本升级后出现诡异不一致（新代码 + 旧数据等）：用 § 4.3 版本号机制破缓存即可，无需用户手动清。

## 一、技术选型

### 1.1 渲染：原生 Canvas 2D（建议）vs 游戏框架

| 方案 | 优势 | 劣势 | 结论 |
|------|------|------|------|
| **原生 Canvas 2D** | 零依赖、可控可调试、团队已有 pixel-canvas 成功经验、像素渲染本质就是 fillRect/drawImage | 摄像机/动画/寻路要自己写（但都是小件） | ✅ **采用** |
| PixiJS | WebGL 批渲染、精灵量大时性能好 | 引入依赖；像素视界精灵数 <100，用不上 | 备选（若未来特效需求暴涨） |
| Phaser | 完整游戏框架（场景/输入/tween/tilemap） | 框架约定重、包体积大、与三分离架构冲突 | 不采用 |

**理由**：本项目渲染负载极小（一屏几十个精灵、几千个矩形），Canvas 2D 绰绰有余；老 pixel-canvas 已验证 120 等分渲染方案流畅。自己写 ~300 行轻量渲染器，换来完全的可控性——"更好的解决方案"不等于更重的框架，而是更对的抽象。

### 1.2 其余延续既定路线

- 原生 JS + 三分离架构（页面 index.html/css/js，类 + destroy()），SPA 路由同 webview 传统
- 手机 H5 优先，120 等分系统级分辨率适配，禁抗锯齿、整数倍缩放、`image-rendering: pixelated`
- 110 色调色板（color.json）为唯一颜色来源
- 数据：明道云为正式存储，demo 期间同结构示例数据

## 二、格子系统（E3"重新想"的提案）

老系统的问题：41x41 的角色是"半屏大图"，适合**展示**，不适合**生活在地图里**（一格屏装不下几个居民，也没有移动的空间感）。所以**地图和角色用两套尺寸、一套调色板**：

### 2.1 双层资产

| 资产 | 尺寸 | 用途 |
|------|------|------|
| **场景小人** | 16x16 像素（占 1 格） | 世界中生活、行走、点击的目标；含 2 帧（待机/行走） |
| **详情大图** | 41x41 像素（沿用 juese.json 规格） | 角色面板、对话头像——点击角色后的"看清他" |

两层都是 110 色调色板内的二维数组（`""`=透明），渲染代码完全同构。

### 2.2 场景格子规格

```
1 格（tile） = 16 x 16 逻辑像素（= 16 系统级分辨率单位）
场景大小     = 48 x 48 格（768x768 逻辑像素，约 6.4 屏宽 x 10 屏高，可滚动）
一屏可见     = 约 7.5 x 13 格（竖屏，GB/宝可梦级视野，角色大小合适）
角色占位     = 1 格（脚下格子 = 位置坐标）
```

- 地形/装饰：也是格子资产（16x16），或装饰物占多格（如 2x2 建筑）
- 碰撞层：二维数组标记不可通行格（水/建筑/边界）
- 点击拾取：点击 → 反算格子 → 命中角色格（含 1 格容差）

### 2.3 世界坐标（两级视图）

**世界层（全景图）不使用格子**——它是抽象布局图：

```json
{
  "world": "天界",
  "scenes": [
    { "id": "tu",   "name": "土局(待定名)", "anchor": [24, 20], "zhushen": "小粽" },
    { "id": "mu",   "name": "木局(待定名)", "anchor": [12, 12], "zhushen": "小风" },
    { "id": "shui", "name": "水局(待定名)", "anchor": [36, 12], "zhushen": "梦瑶" },
    { "id": "huo",  "name": "火局(待定名)", "anchor": [12, 30], "zhushen": "小云" },
    { "id": "jin",  "name": "金局(待定名)", "anchor": [36, 30], "zhushen": "阿说" },
    { "id": "dongcheng", "name": "东城住所", "anchor": [24, 36], "zhushen": "东城" }
  ]
}
```

- 全景图：绘制各局图标 + 名称 + 主神 + 在场角色头像点；**只显示重要信息**（需求明确）
- 进入局后：切到该局的 48x48 格子场景，比例自然放大——"人大小不变，相对变小"自动成立
- **5 Agent ↔ 五局对应关系**：上表是默认建议（小粽-土/中宫、小风-木/生长、梦瑶-水、小云-火/声望、阿说-金/果断），随时可改，只是配置数据

## 三、角色位置与日程系统

### 3.1 位置数据结构

```json
{
  "rowid": "…",
  "mingcheng": "小粽",
  "ju": "tu",
  "tx": 20, "ty": 30,
  "face": "down",
  "zhuangtai": "idle | walk | talk",
  "shiyebanjin": 8
}
```

### 3.2 日程驱动（自主移动的 v1 简化）

```json
{
  "schedule": [
    { "changjing": "tu", "mubiao": [20, 28], "dongzuo": "paideltai", "shiduan": "9-12" },
    { "changjing": "tu", "mubiao": [34, 40], "dongzuo": "paihuai",   "shiduan": "14-18" },
    { "changjing": "dongcheng", "mubiao": [8, 10], "dongzuo": "zhanli", "shiduan": "20-8" }
  ]
}
```

- 状态机：`idle（待机2帧呼吸）→ walk（沿寻路路径逐格走）→ 到达 → idle/徘徊`
- 寻路：48x48 小图，BFS 足够（无需 A* 优化）
- **传呼**：用户点击"传呼"→ 角色打断日程，寻路到用户指定位置 → 对话结束后回归日程
- 位置持久化：角色**切换场景/驻点时**才写一次存储（demo 本地 / 正式明道云），行走过程不写——低频写、前端插值，天然支持未来多人同步

### 3.3 位置 = AI 上下文（需求 F7）

每次对话请求携带：

```json
{
  "weizhi": {
    "changjing": "tu",
    "changjing_miaoshu": "土局·中枢大殿（庄重、承载决策的氛围）",
    "tx": 20, "ty": 30
  }
}
```

demo 的 mock 回复会体现这一点（同一角色在不同局/位置返回不同气质的示例回复），验证"场景即心智"的数据流。

## 六、像素资产生成管线（E1/E2"让 Agent 自主生成"）

**思路**：把"设计能力"变成"约束满足问题"——110 色调色板 + 小尺寸二维数组，正好是 LLM 擅长的格式化输出。

```
输入：角色名 / 地支性格关键词 / 五行 / 主色系（色系行号）
  ↓ LLM 生成（few-shot：给 2-3 个手工小人做示例，要求输出 16x16 数组，只允许该色系行+灰度描边色10）
  ↓ 校验器：值域合法 / 描边闭合 / 主体连通 / 尺寸正确
  ↓ Canvas 预览（2帧并排、放大 8x）
  ↓ Agent 自评+重生成（或人工微调）→ 导出 JSON → assets/characters/
```

- 16x16 = 256 格，token 成本极低，可批量生成 10 版择优；41x41 大图同理（生成难度更高，可先由小人放大打底再细节化）
- 场景瓦片同理生成（16x16 地形块，按"草地/石板/水面+色系"批量产出）
- **demo 期间**：小风直接充当生成者产出 6 个小人 + 1 个局的瓦片集（我生成，人工过目后入库）；管线工具化放 M2
- 颜色纪律（东城要求"颜色不要太多"）：每个角色限制 ≤1 个主色系行 + 灰度描边，全局 110 色兜底

## 九、风险与预案

| 风险 | 预案 |
|------|------|
| 16x16 小人生成质量不稳 | 管线里加"生成N版择优+校验器"；兜底：手绘修正关键帧 |
| 两级视图交互复杂度超预期 | 全景图先用最简布局（图标+文字），交互打磨放 M2 |
| AI 后端方案晚于 demo 到位 | 接口已隔离，mock 完整承载演示；到位后只写 Adapter |
| 48x48 场景内容量不足显得空 | 瓦片批量生成 + 装饰物铺量；场景尺寸可配置（规格不变） |

# ws-server 容量规划与演进路线

> 结论先行：**当前单机纯广播架构舒适区 ≈ 几百人在线**。瓶颈不在 WebSocket 连接数，在广播放大。
> 演进路线分三阶段，阶段 2（分区广播）最贴合孚世界的商家模型，且协议已预留桩子，前端无需改动。
> 撰写：林东城｜2026-09-02｜背景：多端实时同步上线（presence + world.move 广播）后做的容量评估

---

## 一、当前架构（2026-09-02 现状）

```
客户端（N 个页面，ws-bus）
    │  wss://100000whys.cn/ws（Nginx 反代 → 127.0.0.1:8080）
    ▼
Node.js ws 单进程（pm2 守护）
    │  纯广播：收到 → wss.clients.forEach 原样转发
    ▼
所有连接（无分区、无鉴权、无持久化）
```

消息类型（信封 `{ type, from, to, body, ts }`）：

| type | 频率 | 用途 |
|------|------|------|
| `world.move` | 走动时 ~2 条/秒/人 | 每走一格广播一次，各端回放 |
| `world.presence` | 8 秒 1 条/人 | 在线心跳 + 位置兜底校正 |
| `world.chat` | 偶发 | 聊天广播 |

## 二、容量数学：为什么是 O(N²)

设 N 人在线，广播放大系数 = N（每条消息发给所有连接）：

```
出口消息速率 ≈ N × (2N + 0.125N) ≈ 2N² 条/秒
```

| 在线人数 | 入站 | 出站（广播后） | 单机评估 |
|---------|------|--------------|---------|
| 10 | 20/s | 200/s | 毫无压力 |
| 100 | 200/s | 2 万/s | 轻松 |
| **500** | 1 千/s | **25 万/s（~125 MB/s）** | 单进程极限区 |
| 1,000 | 2 千/s | 200 万/s | 崩溃（网卡先爆） |
| 5,000+ | — | — | 纯广播不可行 |

**关键认知**：
- WebSocket 单机几万连接是成熟技术（C10k 已解决）——**连接数不是瓶颈**
- 瓶颈是"5000 人被迫收看另外 4999 人的走路心跳"——99.9% 流量是浪费的
- 结论：**做减法（少广播）永远比做加法（多加机器）便宜**

## 三、演进路线

### 阶段 1：现在（< 500 人）——什么都不做

- 现有架构直接用
- 可选微优化：心跳 8s → 15s；移动广播做 200ms 合并
- **把精力花在玩法上，不要提前优化**

### 阶段 2：分区广播（500 ~ 5,000 人）——最适合孚世界的一步

核心思想：**只广播给"同场景 / 同商家"的人**。

```
服务端加一个房间表：
  const rooms = new Map();  // roomId -> Set<connection>

连接时按 query 参数入房（?org=<商家rowid>&scene=<场景id>）：
  入房(org || scene, ws)

广播时只发同房：
  if (msg.type.startsWith('world.')) {
    const room = rooms.get(roomOf(ws));
    room.forEach(c => c.readyState === 1 && c.send(envelope));
  }
```

**孚世界的天然分区维度 = 商家/组织**：
- URL 本来就带 `org` 参数，用户表本来就有 `shangjia` 字段
- 按商家分房：全平台 1 万人 ÷ 100 个商家 = 每房 100 人 → **单机绰绰有余**
- O(N²) 降为 O(Σ 每房人数²)

更进一步的格子级 AOI（只发视野附近的）是 MMO 标准做法，本阶段通常不需要。

### 阶段 3：分布式（> 5,000 同屏，MMO 级）

- Redis Pub/Sub 跨进程/跨机器转发
- 网关层（连接）与逻辑层（房间/状态）分离
- 或直接采用专业框架：Colyseus / Nakama / Photon / 云厂商 WebSocket 服务

> 到这个量级说明孚世界商业上已经成功了——那是幸福的烦恼，届时有收入有团队，重构不是风险。

## 四、已埋好的桩子（协议不变承诺）

**2026-09-02 起的消息信封已包含分区所需字段**：

```json
{ "type": "world.move", "from": "<rowid>", "to": "",
  "body": { "rowid": "demo-xiaozong", "tx": 15, "ty": 12,
            "scene": "<场景rowid>" },   ← 阶段 2 的分房依据
  "ts": 1788348000000 }
```

- 前端协议（ws-bus + world.* 信封）**保持稳定**，容量演进只改服务端路由
- 前端已做跨场景防护（`applyMove` 校验 `body.scene` 与本地场景不符则忽略）
- 这正是"后端简单传消息、逻辑放前端"路线的红利：**协议稳定，容量问题永远可以在服务端单独解决**

## 五、决策记录

| 日期 | 决策 | 原因 |
|------|------|------|
| 2026-08-30 | 单机 echo 服务上线 | 最小可用 |
| 2026-09-02 | 加 broadcast 分支（world.* 广播） | 像素视界实时移动/聊天需要 |
| 2026-09-02 | 不加 token 鉴权，逻辑前端判断 | 用户拍板：后端保持纯管道 |
| 2026-09-02 | 分区广播列为阶段 2，暂不实施 | 当前量级远未到，org 维度已预留 |

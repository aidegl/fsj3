# 决策流格式 v1 · 定稿（Agent 必读）

> 你是一个 CLI Agent，你干活时会被「决策流」记录——它让老板在像素视界上帝端实时看见你每一步"做了什么、为什么、检索策略是什么"。
> 本文档是唯一必读——读完即可上手，无需读前端代码。
> 撰写：无名｜2026-10-01 定稿 · 2026-10-02 升 **v1.1**｜格式版本：flowVersion 1.1｜老板拍板：命名「决策流」· 约束「混合模式」· **体验感优先（blocked 状态）** · **v1.1：计数进度 + 情绪渲染层 + 动态呈现约定**

---

## 一、30 秒上手

**干活前**：在你的 `workspace/flows/` 下建一个 flow 文件（命名 `flow-YYYYMMDD-<agent>-<序号>.json`），把任务和计划写成 steps。**然后正常干活**——旁边有个常驻 watcher 会自动把文件变化广播到像素视界，你不用管推送。

最小可用示例（直接抄）：

```json
{
  "flowVersion": "1.0",
  "id": "flow-20261001-wuming-001",
  "agent": "wuming",
  "dim": 3,
  "task": "一句话任务描述",
  "status": "running",
  "startedAt": "2026-10-01T14:00:00+08:00",
  "finishedAt": null,
  "strategyNote": "整体检索策略一句话",
  "steps": [
    { "no": 1, "type": "clarify", "title": "确定任务", "status": "done",
      "startedAt": "14:00", "endedAt": "14:03",
      "blockedOn": null,
      "decision": { "chosen": "这么做", "why": "因为…", "alternatives": ["备选A", "备选B"] },
      "output": "一句话产出" },
    { "no": 2, "type": "plan", "title": "制定计划", "status": "running",
      "startedAt": "14:03", "endedAt": null, "blockedOn": null }
  ],
  "revisions": []
}
```

## 二、字段规范

### 流级字段（封面）

| 字段 | 必填 | 说明 |
|------|------|------|
| `flowVersion` | ✅ | 固定 `"1.1"`（1.0 旧文件仍合法，仅缺省 v1.1 可选字段） |
| `id` | ✅ | `flow-日期-agent-序号`，全局唯一 |
| `agent` | ✅ | agent 标识（`wuming`/`xiaozong`/…，对应 WS `from: cli-<agent>`） |
| `dim` | ✅ | **12维编号（1~12）**：这件活属于哪个维度（3业务/8计划/2想法/4交流…），复盘按维度聚合的锚点 |
| `task` | ✅ | 一句话任务 |
| `status` | ✅ | `running` 干活中 / `blocked` 卡住等拍板 / `done` / `failed` / `aborted` |
| `startedAt` / `finishedAt` | ✅/末尾填 | ISO 或 `HH:mm` 均可 |
| `strategyNote` | 建议 | **整体检索策略一句话**——老板要求"计划里能看到检索策略" |
| `steps[]` | ✅ | 至少 1 步 |
| `revisions[]` | 空数组占位 | 改计划必记，见下 |

### 步骤字段（内页）

| 字段 | 说明 |
|------|------|
| `no` | 序号，从 1 递增，**不重排**——页面按 no 排序 |
| `type` | 七选一：`clarify`(定任务) `plan`(做计划) `retrieve`(检索) `execute`(执行) `verify`(验证) `replan`(改计划) `deliver`(交付) |
| `title` | 一句话步骤名 |
| `status` | 七选一：`pending / running / blocked / done / changed / skipped / failed` |
| `startedAt` / `endedAt` | 开始/结束时间 |
| `blockedOn` | **仅 status=blocked 时填**：在等谁、等什么事，一句话（如"等老板拍板：状态机是否加blocked"）。其余时候 `null` |
| `retries` | 可选：本步内同一动作**重试了几次**（检索重试已由 retrievals[] 逐次记录，勿重复计；不重试不填）。页面显示 ↻n 小标；retries≥2 触发焦虑脸；判官算磕绊率 |
| `progress` | 可选：**循环型任务进度** `{ "total": 30, "done": 17 }`——批量活专用，页面渲染进度条；非循环不填。原则：**循环和重试是"这一个活"的内部节奏，记在步骤身上，不另立步骤** |
| `decision` | 决策点（核心价值）：`chosen` 选了什么 / `why` 为什么 / `alternatives` 放弃了什么 |
| `retrievals[]` | 检索证据，**与 retrieval-hit-log.jsonl 完全同构**：`{way, q, hits, top1, rel, miss}` |
| `output` | 一句话产出 |
| `note` | 补充 |

### revisions（变更是一等公民，禁止悄悄改计划）

```json
{ "at": "22:30", "afterStep": 4, "from": "原做法", "to": "新做法", "why": "为啥改" }
```

追加一条 revision 的同时，把对应步骤 `status` 改 `"changed"`（**title 和原描述一字不改**，只改状态标签）。

## 三、状态 × 页面呈现（体验感对照表，前端照此渲染）

| status | 页面图标/颜色 | 老板一眼看到的意思 |
|--------|--------------|-------------------|
| `pending` | ⬜ 灰 | 还没干到这步 |
| `running` | ◉ 蓝色像素转圈圈 | **正在干这步** |
| `blocked` | ⏸ 黄色 | **卡住了，在等我拍板**（blockedOn 说卡在哪） |
| `done` | ✔ 绿 | 干成了 |
| `changed` | ↻ 黄色箭头 | 这步改过设计（详情翻 revisions） |
| `skipped` | ⤼ 灰 | 跳过了 |
| `failed` | ✘ 红 | 砸了 |

> 体验感铁律：老板打开页面，**3 秒内**必须能回答三个问题——现在干到哪了（找 ◉）？有没有卡着等我的（找 ⏸）？改没改过计划（找 ↻）？agent 写 flow 时维护好状态，就是给这三秒供血。

## 四、混合模式纪律（违反 = 老板看到的可视化失真）

**硬约束——必须先写文件再动手的四种时刻**：

1. **开工**：建 flow 文件（status=running，step1 clarify 至少就位）
2. **做完计划**：plan 步骤落盘，含 strategyNote
3. **改计划**：先追加 revisions 再继续干
4. **收工**：status 改 done/failed，填 finishedAt，deliver 步骤写产出

**附加**：**被卡住（等拍板/等依赖）当下就要把步骤标 blocked + 填 blockedOn**——"卡着等老板"是老板最需要一眼看到的状态，拖到想起来才写 = 体验感失真。

**软约束——边做边记**：retrieve / execute / verify 的细节，干完顺手补，不追求实时。

**步骤写/不写——写"活"，不写"动作"（三层过滤）**：

| 层 | 判定 | 例子 |
|---|---|---|
| ✅ 写 | 一句话能向老板汇报的 | "定了技术方案"、"页面视图做完" |
| ❌ 不写 | Claude 工具级动作（读/改文件、跑命令、搜代码） | 读了 app.js、改了 css |
| ⚠️ 检索不占步骤 | 除非检索本身就是这步的主体 | "调研WS方案"算一步；顺手查资料只落 retrievals |

**粒度标尺**：正经的活 5~10 步，小活 3~5 步；**超过 15 步 = 把工具级动作混进来了**，自查。

**铁律**：
- 检索发生必留痕：`retrievals[]` 加一条（和回复末尾命中率表格、hit-log.jsonl 是同一份事实，三处呈现，不是三份记录）
- `rel` 五档与 hit-log 同标准：5=就是我要的 … 1=完全无关；`miss:true` 是金子，照标
- 概览一屏铁律：title/output 一句话，长内容进 note——页面总览超一屏就是你的错
- flow 文件是**工作缓存**（非记忆），按重云轻本纪律随流水 0 点上云，本地保留不删

## 五、WS 信封（watcher 自动发，agent 无需操作，了解即可）

信封格式与像素世界完全一致 `{type, from, to, body, ts}`，服务端零改动：

```
decision.flow  → body: { flowId, agent, dim, event: start|revise|blocked|done|failed, task, status, strategyNote, revisions }
decision.step  → body: { flowId, agent, no, type, title, status, blockedOn, retries, progress, startedAt, endedAt, decision, retrievals, output }
```

- `from` 用 `cli-<agent>`（如 `cli-wuming`）——**不要**用 HAP 真人 rowid（会被上帝端当回声过滤）
- 上帝端页面打开时只能看见"从现在起"的广播（WS 纯管道无回放）；历史回看走 HAP 决策流表（M3）
- `event` 新增 `blocked`：步骤转 blocked 时 watcher 发流级 blocked 事件，页面顶栏可弹提醒（"有活卡着等你"）

## 附录 A · 情绪渲染层（v1.1）

> 铁律：**情绪是页面算出来的，不是 agent 演出来的**——agent 永远不填情绪字段；想表达程度就在 note 里写大白话（"我非常生气"），归详情页显示，不上大屏的脸。脸和文字打架时以脸为准；"有情绪但规则没触发"是宝贵信号：该补触发规则了。

| # | 情绪脸 | emoji | 触发事实（页面自动判定） | 老板一眼读出 |
|---|---|---|---|---|
| 0 | 平静（基线） | 😐 | 无任何信号（空闲 / 步骤间） | 不好不坏，没消息=没坏事 |
| 1 | 开心 | 😊 | flow done / 里程碑达成 | 干成了 |
| 2 | 兴奋 | 🤩 | 长检索后大命中（rel=5 级发现） | 有重要进展 |
| 3 | 焦虑 | 😰 | 连续 ≥2 次检索 miss / 步骤 failed / retries≥2 | 有麻烦，还没认输 |
| 4 | 严肃 | 🫡 | blocked 等拍板 | 停下来，在等你 |
| 5 | 挫败 | 😫 | 连续失败 / flow aborted | 崩了，快来人 |
| 6 | 困惑 | 🤔 | 检索连环打歪（命中全 rel≤2）/ 任务自相矛盾 | 问题可能在任务本身——该重述任务了 |
| 7 | 过载 | 🤯 | 步骤超 15 标尺 / 干太久不收 | 这条 flow 该收尾或该拆了 |
| 8 | 冷却 | 💤 | 限流 / 断线重连 / 等第三方 | **等系统 ≠ 等你**，别急 |

三条铁律：
1. **封顶九张**——加第十张脸必须先减一张；新事实先问能否折进现有九张
2. **脉冲回落**——变脸 10 秒回基线 😐；情绪越罕见越有信息量
3. **强度挂真数字**——不打 1-5 分；程度由事实数字表达（"⏸ 等你 2 小时""连续 miss 4 次"），脸管"哪类事"，数字管"多严重"

## 附录 B · 动态呈现约定（v1.1）

> **数据层管真，渲染层管活**：数据永远整段到达，"动态感"全部由页面负责。

| 分期 | 效果 | 规则 |
|---|---|---|
| M2a（先行） | 节点秒显；◉ 转圈旁**秒表**（已干 X 分 X 秒，页面本地计时，零额外消息）；顶栏"X 秒前有动静"**呼吸灯**；状态切换小动效；情绪九张脸 | 非流式，先把命脉（写文件→广播→页面变色）跑通 |
| M2b（后补，随 Figma 稿落地） | **打字机**逐字吐出（30~60ms/字，>200 字快滚）+ 节点滑入 | **仅限"正开着页面时实时新到达"的节点**；历史加载、详情页、长文一律秒显——打字机是"新鲜标记"，不是处处表演 |

打字机诚实条款：打字机为**放映效果**（数据整段到达后逐字呈现），非真流式，白纸黑字写明不算欺骗；`progress` 跳动与秒表同属本地渲染，零额外消息。

### v1.2 子步字段表

| 字段 | 必填 | 说明 |
|---|---|---|
| `no` | ✅ | 小数字符串（`"2.1"`/`"2.2"`），挂在哪个主步下面就跟谁 |
| `depth` | ✅ | 固定 `1`（主步省略或 `0`） |
| `type` | 建议 | 同主步七选一 |
| `title` | ✅ | 一句话 |
| `status` | ✅ | 同主步七选一 |
| `startedAt`/`endedAt` | 建议 | |
| `note` | 可选 | 一句话；长内容仍回父步 note |
| ~~decision/retrievals/bashen(bage)/emo/demoHits~~ | 禁止 | 子步不挂这些——挂父步；检索必留痕的口径不变（算父步的） |

**心智一句话：任何层级都是「平铺 steps + 可挂子流」；子步=父步的内部清单，拆流=升级成独立活。**

### v1.2 维护纪律（2026-10-19 清创事故后新增）

| 纪律 | 内容 | 防什么 |
|---|---|---|
| **note 定额** | note 只写≤100 字的**结论**；流水/过程记录禁止进 note | note 是"详情页补充说明"（原始设计），不是流水账——实证：s2 note 曾膨胀到 5688 字/47 次堆叠，页面不可读 |
| **收割纪律** | 每轮收尾，把"本轮做了什么"要么压成一句结论、要么升成一条子步；堆叠出现即刻收割 | 廉价路径（往 note 尾巴加一句）总会吞掉昂贵路径（开子步）——47:4 的流量比就是教训 |
| **单写者协议** | 一条 flow 同一时刻只归一个会话写；并行会话各写各的流（需要合流时由流主人收割） | 多写者追加同一 JSON 字段 → 撞车/损坏（实证：并行写导致 JSON 非法） |
| **hook 质量对账** | Stop hook v2：mtime 超 15 分钟 **或** 任一 step note>2000 字 **或**「· 本轮」堆叠>10 次 → 打回，要求收割 | 只验"动了没"不验"动得好"= 激励相容失败，系统在奖励最低质量维护 |

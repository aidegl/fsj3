# 内容权限系统设计文档

> 创建时间：2026-07-04
> 更新时间：2026-07-04（权限模型重构）
> 状态：草稿 - 待测试验证

---

## 一、概述

内容权限采用 **"可见组 + 不可见组"** 的简化模型：
- **可见组**：决定谁可以看（支持多选）
- **不可见组**：决定谁不能看（排除指定用户）

最终可见 = 可见组包含的用户 - 不可见组排除的用户

---

## 二、层级结构

```
商家(App) - 最外层
  └── 组织（多层级）
        └── 子组织
              └── ...
```

- 每个 app 有一个商家 ID（最外层组织）
- 商家下有多个组织，组织可以有子组织（父子关系）

---

## 三、权限选项

### 3.1 可见组（可多选）

| 选项 | 说明 | 存储方式 |
|------|------|---------|
| **公开** | 商家组织下所有用户可见 | kjzz 关联商家最外层组织 |
| **部分可见** | 指定的部分用户可见 | kjzz 关联"部分可见"隐形组织 |
| **组织可见** | 指定组织的成员可见 | kjzz 关联用户选择的组织 |
| **粉丝可见** | 关注我的用户可见 | kjzz 关联"粉丝组"隐形组织 |

### 3.2 特殊选项

| 选项 | 说明 | 互斥规则 |
|------|------|---------|
| **仅自己可见** | 只有创建者可见 | 选中后其他所有选项灰掉 |
| **部分不可见** | 指定的用户不可见 | 任何时候都可选 |

## 四、UI 交互规则

### 4.1 选项互斥逻辑

| 当前选择 | 可选的其他选项 | 灰掉的选项 |
|---------|--------------|-----------|
| **公开** | 部分不可见 | 部分可见、组织可见、粉丝可见 |
| **部分可见** | 组织可见、粉丝可见、部分不可见 | 公开 |
| **组织可见** | 部分可见、粉丝可见、部分不可见 | 公开 |
| **粉丝可见** | 部分可见、组织可见、部分不可见 | 公开 |
| **仅自己可见** | 无 | 其他所有选项 |

### 4.2 规则总结

```
IF 选择"公开" THEN:
    只能再选"部分不可见"
    
IF 未选择"公开" THEN:
    可以多选"部分可见"、"组织可见"、"粉丝可见"、"部分不可见"

IF 选择"仅自己可见" THEN:
    其他所有选项都灰掉
```

### 4.3 高亮显示

- 当多选包含"公开"时，高亮显示：**公开 + 部分不可见**
- 当多选不包含"公开"时，高亮显示：所有已选选项

## 六、权限判断逻辑

### 6.1 判断流程

```
1. 获取当前用户 rowid
2. 获取用户加入的所有组织 rowid 数组
3. 查询内容时过滤：
   
   可见条件（满足任一）：
   - 内容在"公开"状态 且 用户属于该商家
   - 内容.kjzz 关联的组织 包含 用户加入的任一组织
   - 内容.fabuzhe == 当前用户
   
   不可见条件（排除）：
   - 内容.bkjz 关联的组织 包含 当前用户
```

### 6.2 简化版过滤逻辑

```javascript
// 伪代码
const isVisible = (content, currentUser, userOrgs) => {
  // 仅自己可见
  if (content.quanxian === '仅自己可见') {
    return content.fabuzhe === currentUser.rowid;
  }
  
  // 检查是否在不可见用户列表
  if (content.bkjyh?.includes(currentUser.rowid)) {
    return false; // 被排除
  }
  
  // 检查是否在可见组
  // 公开：用户属于商家组织
  if (content.quanxian?.includes('公开')) {
    if (userOrgs.includes(content.shangjiaZuzhi)) {
      return true;
    }
  }
  
  // 组织可见 / 部分可见 / 互关可见
  if (content.kjzz) {
    const hasIntersection = content.kjzz.some(org => userOrgs.includes(org));
    if (hasIntersection) {
      return true;
    }
  }
  
  // 创建者始终可见自己的内容
  if (content.fabuzhe === currentUser.rowid) {
    return true;
  }
  
  return false;
};
```

## 七、隐形组织触发时机

| 触发事件 | 操作 |
|---------|------|
| 创建"部分可见"内容 | 创建"部分可见"隐形组织，添加指定用户 |
| 设置"部分不可见" | 直接将用户存入内容的 bkjyh 字段 |
| 用户A关注用户B | 将A加入B的"粉丝组"隐形组织 |
| 用户A取消关注B | 从B的"粉丝组"隐形组织中移除A |

## 八、API 过滤示例

### 8.1 查询当前用户可见的内容（方案 B · fabuzhe 兜底）

```json
{
  "worksheetId": "6a03ceaa7e29abcb297cbdfc",
  "filters": [
    {
      "controlId": "bkjyh",
      "dataType": 29,
      "spliceType": 1,
      "filterType": 25,
      "value": "<当前用户rowid>"
    },
    {
      "isGroup": true,
      "spliceType": 1,
      "groupFilters": [
        {
          "controlId": "kjzz",
          "dataType": 29,
          "spliceType": 2,
          "filterType": 24,
          "values": ["<用户组织1>", "<用户组织2>", "<用户组织3>"]
        },
        {
          "controlId": "fabuzhe",
          "dataType": 2,
          "spliceType": 2,
          "filterType": 2,
          "value": "<当前用户rowid>"
        }
      ]
    }
  ]
}
```

**语义**：`bkjyh 不含我  AND  ( kjzz 命中我的任一组织  OR  fabuzhe 是我 )`

**三个关键点**：

- `bkjyh` 用 `filterType=25 (RCNe)` 在 **API 层一次排除**，不再需要拿到结果后二次 JS 过滤
- `kjzz` 用 `filterType=24 + values` 数组，用户的多个组织一条条件搞定（详见《HAP复杂过滤请求体指南》3.6 节）
- `fabuzhe==我` 作为兜底分支（方案 B），保证发布者能看到自己的"仅自己可见"内容
- `isGroup` 必须保留：bkjyh 的排除要同时管住 kjzz 和 fabuzhe 两个分支，否则排除会漏

**字段类型备注**：

- `bkjyh` 已确认为关联记录（`dataType=29`），`filterType=25`
- `fabuzhe` 若是**文本**字段 → 如上 `dataType:2` + 真实 rowid（**不能用 `user-self`**，纯字符串比较不生效）；若是**成员**控件 → 改 `dataType:26, value:"user-self"`；若是**关联记录** → `dataType:29, filterType:24`

## 九、前端权限写入映射

查询侧用第八章的请求体统一过滤，复杂度全在**写入侧** —— 发布内容时按权限选项正确组装 `kjzz` / `bkjyh` 字段。

### 9.1 权限选项 → 字段映射

| 权限选项 | kjzz（可见组）| bkjyh（不可见用户）| 前置动作 |
|---|---|---|---|
| 公开（默认）| `[商家rowid]` | `[]` | 无 |
| 仅自己可见 | `[]` 空 | `[]` | 靠 `fabuzhe` 兜底 |
| 部分可见 | `[本次创建的隐性组rowid]` | `[]` | 先建隐性组+加成员 |
| 组织可见 | `[选的组织rowid, ...]` | `[]` | 无 |
| 粉丝可见 | `[发布者粉丝组rowid]` | `[]` | 粉丝组系统自动维护 |
| 多选（部分+组织+粉丝）| 多个 rowid 拼一起 | `[]` | — |
| 叠加部分不可见 | 不变 | `[选的用户rowid]` | 候选剔除自己 |

> 默认公开 = `kjzz=[商家rowid]`。

### 9.2 仅自己可见的深化（fabuzhe 兜底）

仅自己可见的内容 `kjzz` 留空，全靠查询请求体里的 `fabuzhe==我` 这条兜底分支命中。

这个机制要成立，**必须保证发布者永远不出现在自己的 bkjyh 里**。否则：

```
fabuzhe==我  →  命中可见组  →  但 bkjyh RCNe 我 把它排掉  →  自己看不到自己的内容
```

逻辑直接崩溃。

### 9.3 硬约束：bkjyh 候选剔除自己

"用户选不可见用户时不能选自己" —— 这不是体验优化，是**过滤逻辑自洽的硬约束**：

| 约束 | 落实位置 | 作用 |
|---|---|---|
| bkjyh 候选列表剔除当前用户 | 前端选人 UI | 保证发布者不被自己排除 |
| 仅自己可见时灰掉"部分不可见" | 前端互斥逻辑（第四章 4.1）| 避免无意义叠加 |

这条约束**对所有权限都成立**：任何内容的 bkjyh 都不能含发布者自己，否则 fabuzhe 兜底全线失效。

### 9.4 查询侧：统一请求体覆盖所有权限

不管内容是哪种权限，第八章的请求体都能正确过滤，无需按权限分：

| 内容权限 | 命中路径 |
|---|---|
| 公开 | kjzz=[商家]，用户在商家组织 → 命中 kjzz |
| 部分可见 | kjzz=[隐性组]，用户在隐性组 → 命中 kjzz |
| 组织可见 | kjzz=[组织]，用户在组织 → 命中 kjzz |
| 粉丝可见 | kjzz=[粉丝组]，用户是粉丝 → 命中 kjzz |
| 仅自己可见 | kjzz 空，发布者查 → 命中 fabuzhe；别人查 → 都不命中 |
| 含部分不可见 | bkjyh 含该用户 → 被 RCNe 排除 |

前端真正要写代码的就是 9.1 那张映射表 —— 发布内容时按勾选组装 `kjzz`/`bkjyh`，加 bkjyh 候选剔除自己。查询侧一个请求体打天下。

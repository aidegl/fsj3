## 一、世界观

### 1.1 商家即宇宙

每个商家（`shangjia` 表中 `leixing=商家` 的记录）是一个**独立宇宙**——一个完全自洽的世界，拥有：

- 自己的成员（用户 + 智能体）
- 自己的资源（灵力值总额守恒，初始 100 万）
- 自己的配置（主题色、菜单、看板、微信支付）
- 自己的内容（商品、文章、订单、流水）

宇宙之间**严格隔离**：一个自然人在不同宇宙里是不同身份（不同 rowid）。跨宇宙 = 跨世界，靠小程序重载 webview 换 `?shangjia=` URL 参数实现（现状机制），**不是前端切换**。

### 1.2 双轨：用户社会 + agent 社会

同一套组织架构同时服务两类成员：

- **真人用户**：通过小程序使用商城、论坛、智能体对话等功能
- **智能体（agent）**：作为组织的**平等成员**，产生内容、互动、消耗灵力值，像真实社会一样运作

这两类成员共用同一套机制（同一张成员表、同一套组织归属、同一套灵力值体系），靠"成员分类"字段区分。这让平台既能给真人用，也能跑 agent 社会模拟——**这是本项目最核心的架构愿景**。

### 1.3 一切皆内容元数据

平台上所有"信息性"的数据——商品、文章、评论、订单、灵力值流水、积分流水、置信度变动、权重变动——都统一进**内容元数据表**（`shangpin`），靠 `leixing` 区分类型。

新增一种"信息类型"只需加一个 `leixing` 枚举值，不用建新表。这是整个架构简洁性的根基（详见《内容元数据使用指南》）。

## 二、核心概念词汇表

| 概念 | 说明 |
|---|---|
| **商家（宇宙）** | 最外层组织，一个独立世界。`shangjia` 表 `leixing=商家` |
| **组织** | 宇宙内的真实组织单元，可多级嵌套。`shangjia` 表 `leixing=组织` |
| **成员** | 组织里的参与者，三分类：组织用户 / 智能体 / 外部用户 |

| **积分** | 传统增发软通货，做任务/消费即增加。承载行为激励 |
| **权重** | 成员/内容的影响力、展示优先级，通过记录表增减 |

| **组织角色（zzjs）** | 组织级操作权限角色表，创建组织者为 Owner 拥有所有权限 |

## 三、数据结构

### 3.1 商家/组织表（shangjia）

**表ID**：`69f549c69f1956fc0e171aa6`

这是一张**多态表**，用 `leixing` 区分四种角色：

| leixing | 角色 | 含义 | 用途 |
|---|---|---|---|
| **商家** | 宇宙（根）| 最外层 app 实例 | 装配置（color/dbdhl/sjkb/wxappid...），公开权限关联它 |
| **组织** | 真实组织 | 宇宙内的组织单元，靠 `shangji` 字段多级嵌套 | 组织可见权限关联它 |
| **部分可见** | 隐形可见组 | 文章级临时可见组 | 发布"部分可见"内容时建，装指定可见用户 |
| **关注用户** | 隐形粉丝组 | 某用户的粉丝集合 | 粉丝可见权限关联它 |

**字段使用矩阵**（不同 leixing 用不同字段子集）：

| 字段 | 类型 | 商家 | 组织 | 部分可见 | 关注用户 |
|---|---|---|---|---|---|
| `leixing` | 单选 | ✅ | ✅ | ✅ | ✅ |
| `mingcheng` | 文本 | ✅ | ✅ | （自动生成）| （自动生成）|
| `shangji` | 关联(同表) | ❌ | ✅ | ❌ | ❌ |
| `zzyh` | 关联(多·用户表) | ✅ | ✅ | ✅ | ✅ |
| `color` | 文本 | ✅ | 继承 | ❌ | ❌ |
| `dbdhl` | 文本(JSON) | ✅ | 继承 | ❌ | ❌ |
| `sjkb` | 文本(JSON) | ✅ | 继承 | ❌ | ❌ |
| `wxappid/wxsecret` | 文本 | ✅ | ❌ | ❌ | ❌ |
| `icons` | 附件 | ✅ | 继承 | ❌ | ❌ |

> **多态规则**：
> - 只有"商家"类型装配置字段
> - "组织"类型的配置字段留空，前端拿到组织 rowid 后**向上找到根商家**、用商家的配置（Q4=A 决策）
> - "部分可见/关注用户"是隐形组织，只装成员，无配置、无上级

### 3.2 成员模型

成员存在用户表（`69b0077358322d512e60bad0`）里，通过**分类字段**（具体字段名待确认，候选 `juese`/`fenlei`）区分三类：

| 成员类型 | 说明 | 例子 |
|---|---|---|
| **组织用户** | 真人成员 | 普通消费者、社区参与者 |
| **智能体** | agent 成员 | 客服 agent、内容生成 agent、分析 agent |
| **外部用户** | 非本组织正式成员 | 游客、跨组织访客（具体定义待确认）|

三类成员**共用 `zzyh`（已加入组织）机制**，在组织里平等活动：产生内容、互动、消耗/获得灵力值。

> **关键设计**：agent 不是"绑在组织上的服务程序"，而是组织的**成员**。这让 agent 社会运作成为可能——多个 agent 各自持 rowid，像真人一样在组织里活动、留下记录、消耗资源。这与现状（每商家配一个固定 agent）差距很大，是要重点落地的方向。

### 3.3 组织角色表（zzjs）

每个组织有自己的角色集，用于分配**组织操作权限**。注意：这和内容的可见性权限（`kjzz`/`bkjyh`）是两个不同层面。

| 字段 | 类型 | 说明 |
|---|---|---|
| `mingcheng` | 文本框 | 角色名称（如"管理员""编辑""普通成员"）|
| `quanxian` | 多选 | 权限项（具体枚举待确认）|
| `shangjia` | 关联记录 | 所属组织（关联 shangjia 表，角色按组织隔离）|
| `yonghu` | 关联记录 | 持有该角色的用户（关联用户表）|

**关键规则**：
- **Owner = 组织表的 `fabuzhe`**（创建者），拥有所有权限（隐式，无需角色分配）
- 其他成员通过 zzjs 表分配角色，按 `quanxian` 决定能做什么；**一个用户可持多个角色，权限叠加**
- **智能体也走 zzjs**（agent 作为成员同样需要操作权限）
- 角色按组织隔离：每个组织有自己的角色集，靠 `shangjia` 字段区分

**两类权限必须区分清楚**：

| 权限类型 | 控制什么 | 决定字段 |
|---|---|---|
| **内容可见性权限**（读）| 谁能看哪条内容 | 内容的 `kjzz` / `bkjyh` |
| **组织操作权限**（写/管理）| 谁能在组织里做什么操作 | `zzjs.quanxian` |

> 📌 `quanxian` 的具体选项后续再深入，本节先定机制。

### 3.4 内容元数据表（shangpin）

**表ID**：`6a03ceaa7e29abcb297cbdfc`

复用现有内容表（详见《内容元数据使用指南》），在现有 `leixing` 枚举（商品/积分商品/文章/任务/活动/评论）基础上，**新增四个"记录表"类型**：

| leixing 新增值 | 用途 |
|---|---|
| `记录表-灵力` | 灵力值变动流水 |
| `记录表-积分` | 积分变动流水 |
| `记录表-置信度` | 置信度变动流水 |
| `记录表-权重` | 权重变动流水 |

### 3.5 记录表 = 事件溯源

灵力值/积分/置信度/权重都**不存当前余额**，而是存所有变动事件（一条事件 = 一条内容元数据记录）。任意时刻的余额 = 该成员所有相关记录的聚合求和。

这是**守恒的技术保证**：每条灵力值变动记录借贷必平（A 减 X 必然伴随 B 加 X），全宇宙所有记录求和恒等于初始总额，任何时刻守恒可校验。

记录表类型记录的关键字段（推测，待确认）：

| 字段 | 用途 |
|---|---|
| `fabuzhe` | 变动主体（谁的余额变）|
| 数值字段 | 变动数量（待定：复用 `quanzhong`/`jifen` or 新增）|
| `fu` | 关联触发变动的源内容（哪篇内容被采纳导致流动）|
| `mingcheng` / `mdnr` | 变动说明（"上级授灵""内容被采纳"）|
| `shangjia2` | 所属宇宙（隔离用）|

## 四、组织层级

### 4.1 层级结构

```
宇宙（商家，leixing=商家）
  └── 组织A（leixing=组织, shangji=商家）
        ├── 子组织A1（leixing=组织, shangji=组织A）
        │     └── 子组织A1-1
        └── 子组织A2
  └── 组织B
```

层级靠 `shangji`（上级）字段表达多级嵌套，**不限层数**。`leixing` 只区分"是不是商家/是不是隐形组"，不区分层级深度。

### 4.2 可见性规则（默认严格隔离）

**核心规则**：切换到某组织后，**只看该组织的内容**（Q1 决策）。

| 模块 | 切换后只显示 |
|---|---|
| 商城 | 本组织商品 |
| 论坛 | 本组织帖子 |
| 用户列表 | 本组织成员 |
| 消息 | 本组织消息 |

不向下继承（看不到子组织）、不向上继承（看不到父组织）。组织之间是平铺的独立圈子，层级只用于归类和管理。

### 4.3 内容向上提交（机制待细化）

虽然默认严格隔离，但内容可以**主动提交到上级组织**，实现"内容一层层向上流动"：

- 发布内容时默认归属本组织（`kjzz` = 本组织）
- 可选"提交到上级"：提交后内容在上级组织也可见（`kjzz` 改挂或叠加到上级组织）
- 上级内容**不自动回流**下级

**与灵力值凝固模型的关系**：提交内容时，锁在内容里的灵力值连带转移到上级组织——内容带着它的"内在价值"沿层级向上流动。

> ⚠️ 待确认（见第九章）：提交是"移动"（本组织不可见）还是"叠加"（本组织和上级都可见）？谁有权提交？是否需上级审核？

### 4.4 组织切换

| 切换类型 | 范围 | 机制 |
|---|---|---|
| **组织切换** | 同一宇宙（商家）内（Q3 决策）| 前端改"当前组织 rowid"（localStorage + 全局状态），重新拉取组织作用域数据 |
| **跨宇宙（跨商家）** | 不同宇宙之间 | 重载 webview，换 `?shangjia=` URL 参数，全量重跑（现状机制）|

> 📌 **现状**：`home.js:135` 有组织切换的 UI 占位（`show_org_switch`），但未绑任何事件。切换逻辑待实现。

## 五、经济系统

### 5.1 灵力值（守恒硬通货）

| 属性 | 说明 |
|---|---|
| **总量** | 宇宙级恒定（初始 100 万，商家创建时记一条"记录表-灵力"作为初始事件）|
| **性质** | 守恒，只在成员/内容间流转，不凭空产生或消失 |
| **承载** | 价值 / 影响力（稀缺）|
| **流转模型** | 凝固模型（Q1 决策）|

**凝固模型**：
- 发布内容时，灵力值从发布者账户"凝固"进内容（锁入）
- 内容被采纳 / 打赏 / 向上提交时，凝固的灵力值释放给接收者
- 内容天然带"内在价值"，内容流动 = 灵力值流动

**初始分配**（Q4 决策）：商家创建时，100 万灵力值全额记给商家（宇宙主体）持有，由商家或机制下发到组织/成员。

### 5.2 积分（增发软通货）

| 属性 | 说明 |
|---|---|
| **总量** | 不恒定，可一直增加 |
| **性质** | 增发，做任务/消费即产生 |
| **承载** | 行为激励（不稀缺）|

> 📌 现状：积分（`jifen`）已部分落地，1 元 = 1 积分，消费获得，盒子价订单可抵扣。注意《积分系统文档.md》是早期英文设计稿（points/points_log），实际落地的是明道云 `jifen` 字段，两者字段名不一致，以代码为准。

### 5.3 权重与置信度

| 维度 | 含义 | 变动来源 |
|---|---|---|
| **权重** | 成员/内容的影响力、展示优先级 | 上级授予权重、内容被采纳、互动反馈 |
| **置信度** | agent 决策的可信度 | 决策被验证正确则升、错误则降，可追溯 AI 分析思路 |

两者都通过记录表（`记录表-权重` / `记录表-置信度`）增减，任意时刻的值 = 历史记录聚合。

### 5.4 守恒的技术保证

灵力值守恒 = **复式记账**：

- 每条灵力值变动记录必须借贷必平（A 减 X 必然伴随 B 加 X）
- 宇宙内所有成员余额之和 + 锁在内容里的灵力值 = 初始总额（100 万）
- 守恒校验：定期跑聚合查询，若总额 ≠ 100 万，说明有 bug 需排查

## 六、功能模块的组织归属

### 6.1 各模块按组织过滤

引入组织后，现状的"按商家过滤"要细化为"按当前组织过滤"：

| 模块 | 现状字段 | 组织化后 |
|---|---|---|
| 商城/商品 | `shangjia2`（关联商家）| + `kjzz` 命中当前组织 |
| 社区/内容 | `shangjia2` + `shangjia1`（上架）| + `kjzz` 命中当前组织 |
| 用户列表 | （无组织过滤）| `zzyh` 包含当前组织 |
| 消息 | （无组织过滤）| 按当前组织过滤 |
| 订单 | `shangjia`（关联商家）| + 当前组织 |

查询请求体复用《内容权限系统设计文档》第八章的方案 B（`kjzz RCEq 用户组织 OR fabuzhe==我` 且 `bkjyh RCNe 我`）。

### 6.2 字段统一方向

现状 `shangjia` / `shangjia1` / `shangjia2` 三种字段混用，组织化时建议归一：

- `shangjia2`（关联商家）保留，作为"所属宇宙"
- 新增/复用 `kjzz`（关联组织）表达"所属组织"
- `shangjia1`（上架布尔）保留语义不变

> ⚠️ 这是个重构项，影响所有列表查询，需单独立项。

## 七、与权限系统的关系

本架构的 `leixing` 四类型 + 成员机制，正好支撑《内容权限系统设计文档》的权限模型：

| 权限选项 | 实现方式（关联 shangjia 表的哪种 leixing）|
|---|---|
| 公开 | `kjzz` 关联 `leixing=商家`（宇宙根组织）|
| 组织可见 | `kjzz` 关联 `leixing=组织` |
| 部分可见 | `kjzz` 关联 `leixing=部分可见`（隐形组）|
| 粉丝可见 | `kjzz` 关联 `leixing=关注用户`（粉丝组）|
| 仅自己可见 | `kjzz` 空 + `fabuzhe` 兜底 |
| 部分不可见 | `bkjyh` 关联用户（候选剔除自己）|

**隐形组织创建时机**：

| 触发事件 | 操作 |
|---|---|
| 发布"部分可见"内容 | 创建 `leixing=部分可见` 的行，加指定成员 |
| 用户A 关注 用户B | 把 A 加入 B 的"关注用户"组织 |
| 用户A 取关 用户B | 从 B 的"关注用户"组织移除 A |

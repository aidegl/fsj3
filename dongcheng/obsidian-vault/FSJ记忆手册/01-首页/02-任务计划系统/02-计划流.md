# 计划流

计划流
计划流的特点
唯一性
一个任务只有一个计划流，对于Agent来说它的任务是自己创建的，任务的源头端可能委派给多个Agent完成，但是对于Agent它只能看到一个任务，这就是计划流的唯一性。
不可逆
定好的任何和计划流的step一旦执行过就不可修改，落子无悔。有问题可以编辑后面的步骤。
流步骤
一个流有多个步骤，也称step。agent只能执行一个step。
为了不限制agent自由发挥的能力，只硬约束四个时刻（开工/计划落盘/改计划/收工）+ Stop hook 对账打回
一个任务的计划就是逐个完成的；但是可以同时进行多个任务。
什么时候用
计划流不是必须维护的，只有在像素视界上帝端上帝端切角色的rowid为该Agent时才需要维护计划流。之所以不硬性要求维护计划流是担心计划流的规范要求限制了Agent的自由思考和自主能力。在需要东城共同维协同时能凸显其价值。
计划流是什么
一句话：计划流 = agent 的执行队列——agent 照它干活、干完即改状态，老板通过像素视界上帝端毫秒级看到全部过程。每一步「做了什么、为什么、检索策略是什么」全程可溯源，不像裸 CLI 执行完就删。
核心概念
P = 拼图（7目标）：每块拼图是一个目标；任务列表里的每张卡都标注它服务的 P 几
s = 拼图上的图案（8计划）：计划条目与流步骤统一用 s 编号，层级靠上下文区分
module = 本步采用的荣格模块：Ti 逻辑校验 / Te 排程 / Si 翻旧例 / Se 现场直取 / Ni 看主线 / Fe 协作……agent 自定义设计
status：todo → running → done；blocked = 困惑卡点（blockedOn 写清等谁等什么）
decision = {chosen, why, alternatives[]}：溯源核心——做了什么/为什么/放弃了什么
实时闭环
agent 写 json（任意工具调用）→ fs.watch 毫秒捕获 → WebSocket/SSE 推送 → 上帝端页面即时重绘。轮询已废除。
铁律五条
step 只能一个个执行：同一时刻执行型 step 只有一个 running（持续观察型标 continuous，不受此限）
卡住 ≠ 停工：blocked 后跳别的拼图继续干，链路不停
每条对话即时入账：对话产生的新事项马上加进 plan/flow，不等收尾
照 json 执行：json 是执行队列不是事后笔记——先改状态再干活，或同步改
改完自检：语法检查 + 函数存在性对账，防静默死
